# Logging, diagnostics and engineering reports - Phase 8

Use only local simulators and isolated test equipment. Reports document application observations; they do not certify production equipment.

## Search structured logs
1. Open **Reports & diagnostics**. Existing **Activity** remains available with its unchanged export.
2. Enter text, an exact severity/category and optional local-time start/end. Choose **Search logs**. Text matches the structured event body and IDs. Search is literal, not a regular expression. Pagination shows 100 events per page.
3. Expand Details for correlation IDs, counts, measured durations and error classifications. Successful client read/write transactions, successful data verification and routine bridge cycles are DEBUG; they are omitted from structured logs at the default INFO level. The original evidence stores still record them independently.
4. Export filtered JSON or CSV. Export covers all retained matching events, not just the displayed page. Search/exports use a database read snapshot; new events appear after refresh. The page refreshes on request so typing/filter selections are not overwritten by polling.

Categories: application, communication, protocol, simulation, verification, security, recovery and bridge. These are application client/worker observations, not passive PLC discovery, a serial sniffer or a complete wire packet capture. A transaction event gives an actual transaction ID/counts; inspect Communication verification or a communication report for point-level service outcomes. Simulation logs include worker lifecycle; verification logs include scenario-step results. Protocol errors include recorded failed/uncertain client outcomes. Security events include local host/origin/session-token denials and observed protocol authentication/security failures; this does not add user accounts, roles or certificate-management functions from Phase 9.

## Logging policy and retention
Choose **Logging & retention**. Defaults: INFO, 10,000 searchable rows, 30 days, 1,000,000 bytes per JSONL file and three rotated copies. Supported bounds: 100-50,000 rows, 1-365 days, 64,000-10,000,000 bytes/file, 1-10 rotated copies. Levels are DEBUG, INFO, WARNING, ERROR, CRITICAL. Security events and logging-policy changes are retained even when below the configured minimum.
Applying policy may immediately remove older searchable events and excess/old rotated files. Export evidence first. Searchable SQLite rows are pruned by age and row count at startup, emission and search. Rotating JSONL files are independently bounded by size/copy count; old backup files are removed by file age. The active JSONL file can contain older rows until rotation; this is not a per-record erasure guarantee for every disk copy. SQLite files may retain allocated pages after row deletion. Legacy application.log has its existing independent rotation and is not rewritten, retroactively redacted or managed by these controls.
The UI reports write-failure count and the last structured-logging error. Logging failures are caught so they do not abort protocol operations; missing log evidence must not be interpreted as success. Events above 32 KB retain a marked truncation notice instead of oversized details. DEBUG/disk logging adds I/O and can affect cycle timing. Do not use it as a hard real-time guarantee.
Known configured secrets, credential keys, credential assignment patterns and embedded URL credentials are redacted from new structured events/reports. Actual authentication headers and request bodies are not logged for denied requests. This is best-effort redaction, not proof that arbitrary free text cannot contain confidential information. Values, tag names and endpoints can still be sensitive. Protect the local data directory, catalogue snapshots, backups and exports.

## Create a report
1. Collect real evidence with the existing tests, simulations, communication, performance, verification, recovery or bridge tools. Report creation never contacts a device or starts a job.
2. Select **Create report**, choose the source type and template. Optionally enter an exact source ID. Use a run ID from Test runs for one test report. The job filter applies only to simulation, data verification and bridge reports. Choose 1-1,000 source records; default 100. Preview explicitly identifies limited source windows.
3. Choose **Preview actual evidence**. Review the overall result, source row verdicts, retention/window metadata, fingerprint and expandable recorded details. The UI shows the first 50 rows and limits long detail text to 20,000 characters; complete captured evidence remains in exports.
4. Choose **Save reviewed report** to save the exact immutable snapshot. Preview expires after ten minutes, app restart, or eviction beyond ten pending previews. Changing live evidence after preview never changes the saved report. Do not resubmit a modified report body: the API accepts only the server-issued preview ID.
5. Saved history offers View report and PDF/CSV/JSON downloads. History persists across app restarts, including custom templates. Capacity is 200 reports / 100 MB; saving stops with an explicit error when full. No automatic saved-report deletion or archival manager is added. Preserve/export the data directory before manual maintenance.

## Evidence sources and verdicts
- **Test:** durable scenario runs. PASSED -> PASS; FAILED/ERROR -> FAIL; cancelled/running/incomplete -> INCONCLUSIVE. The actual scenario revision, fingerprint, attempts and recorded observations are included when available. Connection snapshots are excluded. Old runs can lack modern metadata. Exact run selection avoids loading unrelated history; large selected evidence over 5 MB is rejected rather than silently shortened.
- **Simulation:** retained completed workspace simulation/server runs and their real lifecycle/cycle counts. An observed ERROR is FAIL. Completed cycles alone are INCONCLUSIVE, because lifecycle does not prove value correctness. Zero cycles are NOT TESTED. Scenario-owned job details belong to the test report; simulation history is the workspace history only.
- **Communication:** retained client read/write transactions, point/batch statuses, real timestamps and measured duration. Good service acknowledgement is PASS within this service-outcome scope; failed points are FAIL, unknown/partial uncertain outcomes INCONCLUSIVE, unsent operations NOT TESTED. Acknowledgement is not independent readback or physical delivery.
- **Performance:** current recorded measurements/history, rate/latency/resource counters and existing alerts. No new pass threshold or benchmark is invented. With recorded samples it is INCONCLUSIVE; without samples it is NOT TESTED. Existing performance scope/retention applies; source ID is performance-snapshot.
- **Data verification:** retained verification checks with actual expected/observed values and their existing PASS/FAIL/INCONCLUSIVE outcome.
- **Recovery:** retained worker recovery/session events and controller snapshots. Events alone remain INCONCLUSIVE; exhausted retries are FAIL. A RECOVERED event is not process-correctness proof. Existing outage/retry/unknown-write evidence is preserved.
- **Error:** retained structured ERROR/CRITICAL events. Recorded errors are FAIL in the error-record scope. No matching error evidence is NOT TESTED, never proof of an error-free system. The source window is at most the most recent 1,000 ERROR plus 1,000 CRITICAL events, then the selected source limit. Minimum level/retention may omit evidence.
- **Bridge:** retained mapped cycles, transformations, source/read/write IDs and destination outcomes. Failed/transform-error points are FAIL; unknown/unsent or mixed acknowledged/filtered outcomes INCONCLUSIVE; acknowledged-only eligible writes PASS; filtered-only cycles NOT TESTED because no new delivery is established. A filtered row is not silently treated as a fresh successful write.

Overall aggregation: any FAIL -> FAIL; otherwise any INCONCLUSIVE -> INCONCLUSIVE; all NOT TESTED/empty -> NOT TESTED; mixed PASS and NOT TESTED -> INCONCLUSIVE; otherwise PASS. These labels describe captured evidence, not a universal verdict about a PLC or installation.
Except durable test history and structured error logs, underlying evidence is process-local and clears on restart/eviction. A saved report preserves what was captured. Source windows/counts/limits are included. Missing, expired or filtered-out evidence is never filled with synthetic measurements. Narrow/empty selections can legitimately produce NOT TESTED.

## Templates, formats and integrity
Report templates control a name, source type, title and scope note only. They cannot supply evidence, formulas, scripts or verdicts. Create/update up to 100 custom templates; eight built-ins remain. Updating a template affects future previews, not saved reports. Import/export or sharing of report-template definitions is not added; scenario templates remain unchanged.
JSON contains the full captured report. CSV flattens the same evidence into JSON-pointer field paths, preserving nested observations; text that could be interpreted as spreadsheet formulas is prefixed with an apostrophe. PDF uses paginated A4 pages, a verdict/ID/fingerprint summary and the captured evidence. Non-ASCII source text is escaped as Unicode codepoints for portable rendering; JSON preserves Unicode. This is an evidence appendix, not a custom dashboard/chart designer.
A report is limited to 5 MB; PDF export additionally limits 10,000 flattened fields. For larger evidence, narrow the selection, use JSON/CSV or use the existing full run/evidence exports. Downloads do not initiate device I/O. PDF rendering runs outside the application event loop. A failed PDF export does not erase the saved report.
SHA256 identifies the redacted captured JSON before the fingerprint field is appended. It is not a digital signature, tamper-proof archive, signed approval or legal certification. PDF binary metadata can change between renders while the evidence fingerprint stays the same.

## Files and deployment
New data: structured-logs/events.sqlite3, rotating events.jsonl files and logging settings; engineering-reports.sqlite3 for saved reports/templates. Application data remain independent of the workspace project JSON. Existing scenarios/adapters/GUI and CSV formats are preserved.
PDF requires ReportLab 4.4.9, added to source requirements.txt. This Mac acceptance environment used Pillow 13.0.0 and charset-normalizer 3.5.2 as its dependencies; notices are in packaging/reporting-dependencies. Future OS packages must resolve/bundle/test these dependencies. Existing installers and Windows offline runtime manifests have not been rebuilt or natively qualified in Phase 8.

## Troubleshooting
No events: check minimum level, category/text/time filters and write-failure health. Successful operations are DEBUG. No report rows: check source ID, job scope, process restart and retention. PDF too large: narrow the source window or use JSON/CSV. PDF unavailable: install the source requirements in the correct runtime; existing distributed archives do not gain Phase 8 automatically. History full: export/archive the local application data; there is no in-app history purge. Preview expired: generate a fresh preview; saved reports remain available independently.

Stop after Phase 8. Phase 9 security/access-control work requires separate approval.
