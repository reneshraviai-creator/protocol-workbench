# Performance dashboard — Phase 4

## Open the dashboard
Choose Performance in the existing sidebar. It observes the running app and does not start jobs or contact devices. It shows measured request/response rates, operation outcomes, point throughput, batch duration statistics, process resources, admission queue state and threshold events. Inspect individual batch evidence opens the existing Communication verification panel, which retains per-request execution times and point outcomes.

## What the numbers mean
Requests and responses count outbound client data-service attempts and received service responses. A rejected response still counts as a response. They are measured at the adapter service boundary, not verified network packets; a connection failure before the underlying library sends a packet can still be a submitted service attempt. Discovery, metadata/preparation, connect/keepalive, subscription notifications, inbound simulator services and HTTP dashboard requests are excluded from these protocol counters.
Successful operations are whole read/write calls with all points acknowledged and no raised error. Operations with failed points have at least one confirmed FAILED point (or a response-validation error). Operations with unknown points have unresolved point outcomes. The latter two counters can overlap on a mixed batch; do not add them as disjoint totals. Pre-dispatch cancellation/queue rejection leaves points NOT_ATTEMPTED, not FAILED or UNKNOWN. Point throughput is attempted data points per second, with successful, failed and unknown rates shown separately. These are not byte rates or guaranteed PLC update rates.
Rates use the current and nine previous one-second buckets, divided by elapsed app-monitor time up to ten seconds. Bucket edges are approximate to one second; idle periods decay to zero. They are not instantaneous network samples. Batch durations are actual application-level elapsed service attempts, including failed/no-response attempts. They exclude admission waiting, connection and preparation. Transaction duration in Communication verification includes admission waiting. Durations enter the performance window when the containing transaction completes.
Average, median, min, max, P95 and P99 use up to 10,000 batch durations from transactions completed in the last 60 seconds. P95/P99 use nearest rank; one sample gives the same percentile as its duration. No samples means Unavailable, not zero latency. Queue waiting and rejected operations have separate cumulative counters.
CPU measures process CPU time against elapsed wall time as percent of one core. It may exceed 100% on multicore workloads. Initial intervals shorter than 100 ms are unavailable to avoid meaningless startup ratios. Memory is current resident/working-set MiB from the native process API (procfs on Linux, mach_task_info on macOS, Windows process memory API). If unavailable, the dashboard says so; it never substitutes zero or historical peak memory as current memory. Only the host used for this phase was validated; the Windows/Linux native probes still require native release qualification.
Active tasks counts all unfinished asyncio tasks on this event loop, including the sampler and HTTP/monitor/recovery tasks. Active client operations counts admitted client data read/write calls; it does not count connected but idle clients. Event-loop lag is measured against the sampler's intended wake-up. Sampling runs about once per second; a blocked loop delays the sample and records that delay when it resumes. It cannot detect a complete process crash in-process.

## Configure batches
Connections → Configure → Batch size settings. Stop the affected job first. OPC UA accepts 1–1,000 points per batch, default 50; smaller advertised server MaxNodesPerRead/Write limits take priority. Modbus accepts 4–120 contiguous units (registers or bits), default 120. Gaps/area changes split requests, whole scalar values remain intact, and existing protocol limits are preserved. Raising a batch cap is not proof a device can handle it: use an isolated simulator first. Saving settings never starts a device operation; adapters use the settings on their next opening.

## Configure concurrency, rate and backpressure
Performance → Configure controls & alerts. Stop workspace jobs, scenario runs, live monitors and manual data operations before changing global performance settings. Save settings persists them in this workspace; existing connection/job configuration remains unchanged. A scenario uses the host application's current global admission policy; its snapshot does not silently replace the application's controls.
Admission is OFF by default, preserving existing scheduling. When enabled:
- Maximum concurrent client operations: 1–64, default 8. This controls simultaneous whole adapter read/write calls across clients, not batches within one call. It does not make a single client's batches parallel.
- Maximum waiting operations: 0–4,096, default 128. Zero means no waiting slots. When full, a new operation is rejected before dispatch; the limiter never drops an already-sent write or automatically retries it. The existing job recovery/failure handling applies. A pre-dispatch BackpressureError is a configuration/pressure error and stops the job for review; it does not falsely mark a write as received.
- Maximum starts per second: 0–10,000, where 0 is unlimited. Nonzero rates space logical data-call starts without a burst. One operation can contain many service requests, so this is not a network request/s ceiling. Concurrency and rate limits both apply. Waiting is cancellable; Stop releases a waiting/admitted slot through the normal lifecycle. No FIFO ordering or fairness guarantee is made across independent callers.
The global queue holds references to waiting calls, not a disk-backed spool. It creates no replay backlog. Low limits can reduce throughput, delay freshness checks or cause cycle overruns. Existing job intervals (0.1–3,600 seconds), monitor polling/publication intervals, server limits, serial ownership and recovery policies still apply. Configure intervals in their existing job/monitor forms; admission controls do not override subscription publishing or simulator-server timing.

## Thresholds and alerts
Set CPU, resident-memory, loop-lag, P95 duration and queue-percent thresholds in the same form. Zero disables a threshold. Alerts are HIGH/CLEARED transitions from actual one-second measurements; HIGH does not repeat every sample. If a previously breached metric becomes unavailable, an UNAVAILABLE event replaces its active breach indication, not a false CLEARED result. Threshold alerts are diagnostic only: they do not stop communication or change device values. Brief spikes between samples may not be observed. P95 thresholds depend on retained sample availability, not a service-level guarantee.

## History, charts and exports
History retains up to 3,600 samples, 10,000 batch durations and 500 alert transitions in process memory. It clears on app restart. The GUI requests only the latest 120 samples to bound polling payloads; JSON and CSV export include all retained samples. Charts use actual time positions and the last 120 samples. JSON includes totals, settings, sampled metrics, alerts, queue statistics and scope. CSV contains numeric sample rows with labelled units and the native memory-source description. Export before restarting if you need evidence. Counters are diagnostic evidence, not a durable audit log or billing record.

## Troubleshooting
No protocol activity: resources still sample, but rates are zero until a client data job/monitor/manual read/write runs. A local server job alone does not produce outbound-client counters. UA subscriptions may receive many values while client-data request rates stay zero; subscription traffic is outside this scope.
High latency with unknown points: inspect Communication verification and Communication health before resuming any write. Performance counters never turn unknown outcomes into failures or authorize replay.
Queue rejections: reduce caller load or review the concurrency/queue/rate settings while stopped. Increasing capacity is not a substitute for a device's limits.
High loop lag or CPU: reduce job frequency/tag count or investigate blocking tasks. Export the measurements. The monitor runs inside the process, so a complete freeze can stop updates.
Unavailable memory/latency: inspect the source/status; missing measurements are not zero usage or fast communication. Sampler errors are visible in the status count.
Settings cannot save: stop the jobs, scenarios, monitors and in-flight manual operations first. Saving unrelated configurations can still use the existing independent workflow.

## Qualification
This phase adds no dependency, production readiness certification or installer rebuild. Local OPC UA and Modbus TCP, existing virtual RTU regression, negative cases and actual instrumentation overhead measurements are documented in the phase report. No new physical PLC, serial adapter, native Windows/Linux installer or endurance qualification is claimed. Use the existing local-simulator/isolated-test-equipment scope.
