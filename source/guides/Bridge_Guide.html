# Protocol bridge and data transformation — Phase 6

## Create and operate a bridge
1. Add the source and destination connections and tags using the existing tools. Confirm actual NodeIds/registers, scalar datatypes, access and word order. Generation does not create a PLC DB.
2. Open Protocol bridge → Create bridge. This opens the existing gateway job form. Choose source/destination, update interval and mappings. Exact matching names may be suggested; review them. Save configures a stopped route, never starts it.
3. Map tags & addresses opens the existing mapping editor, including per-map scale, offset and numeric clamps. Addresses and datatypes come from the selected tag definitions; edit those stopped connection definitions when the actual device map changes.
4. Transforms & metadata adds unit conversions, expressions, Boolean conversion, output filters, change-only delivery and optional source semantics. Preview transform uses the entered sample offline; it does not connect to a device or prove the real value will pass.
5. Start any intended local simulator servers separately, then Activate the bridge explicitly. Deactivate stops its existing worker and retains last destination values. Connection health/recovery and Performance continue showing actual communication. Recovery belongs to the route's destination connection.
6. Inspect delivery evidence and existing Communication verification/Data verification. Export needed evidence before restarting. Saving/editing an active route remains protected; stop it before changing mappings or policies. Independent existing configuration workflows remain available.

Routes use the existing gateway engine and adapters for OPC UA↔OPC UA, OPC UA↔Modbus and Modbus↔Modbus, with TCP/RTU settings and ownership rules preserved. Two sides of an RTU gateway require separate serial ports. A route cannot make an input register/discrete input writable or bypass OPC UA access/certificate settings. No server is silently started and no destination values are reset by stopping.

## Deterministic conversion order
For numeric destinations: typed source → unit preset → optional expression → scale and offset → optional clamps → datatype/Boolean conversion → output filters. Every enabled mapping is transformed before the first destination write in that cycle. A transformation error prevents the whole cycle's destination write, leaving valid peers NOT_ATTEMPTED. Earlier successful cycles are not undone. Once the actual write begins, the destination may acknowledge only part of a multi-request operation; use per-point outcomes rather than assuming atomic device delivery.
Scale/offset and existing min/max clamps retain their original behaviour. Clamps change the value; filters omit a value. Unit presets are none, C_to_F, F_to_C, bar_to_kPa, kPa_to_bar, Pa_to_bar, ms_to_s, s_to_ms, rpm_to_Hz, Hz_to_rpm, percent_to_fraction and fraction_to_percent. Choose the matching engineering convention explicitly; the app does not infer conversion from a unit label. Units printed on tags are labels, not proof that the physical value uses that unit.
Numeric scalar conversions validate the destination range and finite representation. Decimal calculations preserve integer inputs/scale values without first converting them through JavaScript floats. Preserve large Int64/UInt64 constants as strings in JSON/templates. Existing integer cast behaviour truncates fractional numeric values rather than rounding them.
String destinations support identity/canonical scalar text or a compatible String expression, without numeric unit/scale/clamp. Numeric String sources can be parsed for numeric destinations; invalid text stops the cycle before writing. Boolean text true/false is supported for Boolean destinations. DateTime supports OPC UA DateTime identity, DateTime→ISO String and timezone-aware ISO String→DateTime. Numeric DateTime conversion/expressions are rejected. Modbus String/DateTime remain unsupported by the existing register encoding.

## Expressions
Use variable x. Allowed operators: +, -, *, /, %, comparisons, and/or/not, unary +/-, and a conditional such as `1 if x > 10 else 0`. Calls are limited to abs, min and max, with at most eight arguments. Examples: `x * 2 + 1`, `max(0, min(x, 100))`, `x != 0 and 10/x > 1` or, for a String destination, `x + "_OK"`.
Expressions are manually interpreted; there is no Python eval, import, attribute access, indexing, assignment, comprehension or exponentiation. They are limited to 400 characters, 80 AST nodes and depth 20; String literals to 256 characters and output Strings to 4,096. Numeric arithmetic uses a bounded decimal context. No clock, random state, files or network are available to expressions. Bad syntax, division by zero, unsupported operations, invalid text and out-of-range results produce explicit errors and no write for that cycle.
An output filter expression uses the converted output as x and must return a Boolean. Numeric results are not implicitly accepted as filter decisions. Boolean operators short-circuit. A String source remains text in an expression unless an allowed numeric operator converts it; there is no unrestricted function-call facility.

## Boolean modes
strict keeps the original destination conversion, accepting Boolean/0/1 (and compatible true/false text). nonzero is true when the transformed numeric value is nonzero. threshold compares the transformed numeric value against the configured threshold using >=. invert reverses a valid Boolean/0/1 value. equals compares the raw typed source with the configured JSON literal; it cannot combine numeric transforms. Enter JSON true, 1 or "RUNNING", matching the source datatype. Unit/expression/scale/clamp precede numeric threshold/nonzero conversion.

## Filters and change-only delivery
Optional output minimum/maximum filters skip results outside those bounds; filter expression skips false results. Disabled mappings are recorded FILTERED and their unavailable remote NodeIds are not prepared/read/written. Configuration IDs and datatype compatibility are still validated. The resource registry conservatively reserves configured destination mappings until the route stops, including disabled mappings, so conflicting writers remain blocked.
Change-only compares against the last acknowledged output, not the current destination's actual value. It also compares requested forwarded metadata: a new source timestamp/status is a change when forwarding is enabled. Unknown/failed writes never populate this acknowledgement cache. An observed reconnect clears the cache so a new destination session receives a fresh baseline. External destination changes are not detected or automatically corrected by change-only mode. All-filtered cycles perform no destination data write and do not verify unwritten points as delivered. Other polling/connection operations can still occur. When everything is filtered, the destination may be idle; its last observed connection state is not a continuous liveness guarantee. Filters do not delete or reset destination values.

## Timestamps and quality differ between protocols
Default bad-quality policy is stop, preserving existing behaviour. filter explicitly omits non-Good OPC UA source values. preserve requires OPC UA source AND destination plus explicit quality forwarding. It still requires a valid value compatible with the transformation: a Bad status accompanied by a Null/invalid value cannot be numerically transformed or replaced with an invented good value. Some servers deliberately remove the value when status becomes Bad; use filter/stop or correct the source in that case.
Forward actual source timestamp and Forward actual source StatusCode are separate opt-in OPC UA→OPC UA settings. Missing metadata is an error; the app does not replace a missing source timestamp with the local clock. Destination servers may reject a DataValue containing metadata (for example, with BadWriteNotSupported). The normal transaction evidence records that rejection; there is no silent value-only fallback. ServerTimestamp is not forwarded as a source timestamp.
Modbus carries registers/bits without native source timestamp or semantic process quality. Its successful transport/register response is not an OPC UA process-quality field. Forwarding settings involving Modbus are rejected instead of inventing equivalent metadata. Default Modbus→UA value writes do not claim source-quality/timestamp preservation.
A Good write acknowledgement for a metadata-bearing DataValue means the destination service accepted that request. It does not independently prove the remote server retained every field. Inspect destination metadata to qualify its actual behaviour. The local tests checked real UA timestamp and Uncertain-status forwarding. Preserved non-Good values can intentionally fail readback verification; choose an explicit suitable verification policy, or disable value readback when evaluating status forwarding separately. Bad source quality is never silently made Good by the bridge.

## Recovery and delivery evidence
Existing Phase 3 recovery applies: hold unknown writes by default; explicit repeat-safe policies can resume latest values or retry only confirmed transient failed points. Metadata and original source transaction correlation are retained for confirmed-failed retries; retry records link to their original cycle. A configured source-age limit is rechecked against captured timestamps before retrying. The bridge never treats an unknown write as a failed write suitable for automatic replay.
Delivery rows retain source observation/value/quality/timestamp, source and destination tag/type/target/unit labels, transformation snapshot, expected output, requested forwarded metadata, destination point outcome, read/write transaction IDs and measured cycle duration. SUCCEEDED is a destination service acknowledgement, not physical process delivery or independent readback. FAILED is an explicit rejected result; UNKNOWN is unresolved; NOT_ATTEMPTED means no write evidence for that point; FILTERED and TRANSFORM_ERROR are separate. Read/transform failure before writing cannot fabricate destination success. Read failure evidence points to the source transaction when available.
Measured cycle duration covers the source read, transformation and write attempt, or the failed portion before completion. It excludes connection/preparation, retry/backoff waits and subsequent optional readback verification. Existing health metrics record connection recovery separately; Performance records actual batch/operation rates. All-filtered cycles can have valid cycle timings without a write transaction. A route state can stop/error after an acknowledged write because later verification failed: inspect both evidence panels.
History retains 200 cycles / 20,000 point rows, with cumulative point totals and eviction counts. A large cycle can evict earlier ones. The list pages 25 cycles and detail pages 100 points. History is process-local and clears on restart. JSON/CSV exports can include private process values. CSV protects formula-like text; import exact 64-bit values as text in spreadsheets. History is diagnostic evidence, not a durable audit log. Independent scenario engines use the shared app evidence context when run in the app; their worker recovery remains individually identified.

## Reusable mapping templates
Mapping templates opens local save/update/duplicate/delete/import/export. Export current JSON preserves the entire advanced mapping and source/destination names, expected datatypes and address snapshots; it omits connection URLs, credentials and job IDs. The existing CSV mapping workflow remains for basic source/destination/scale/offset/clamp routes; it refuses advanced export rather than silently dropping transformation settings. Use JSON for complete round trips.
A template resolves exact tag names and canonical datatypes against the currently selected route devices. It rejects missing names or changed types. If an address snapshot differs, Review lists template versus current targets. Applying uses current tag definitions and does not silently overwrite addresses; review the listed targets before Apply reviewed mapping. The project save then performs complete validation and existing active-job checks. Applying/importing never starts communication.
Up to 200 active local mapping templates are kept in this workspace data directory. Delete requires confirmation and retains a copy under bridge-templates/trash; there is no in-app trash restore UI. Templates are separate from mixed-tag and scenario/community templates and are not published online. Review is required again after selecting or importing another template.

## Troubleshooting and qualification
TRANSFORM_ERROR: inspect its mapping snapshot and test the actual typed sample offline. Correct expression/unit/range/type, then explicitly restart the corrected route. Valid peers were not written in that failed transform cycle.
UNKNOWN: inspect Communication verification and Communication health; do not assume it is safe to resend. Stop does not undo a previous external write.
FILTERED: check disabled maps, output bounds/filter expression, non-Good policy and change-only cache. The destination retains its previous value.
Metadata rejection: confirm both sides are OPC UA and the destination supports timestamp/status writes. Qualify support rather than accepting a silent fallback. Missing/Null source values cannot be converted into valid numeric readings.
No delivery evidence: configuring or previewing does not run a bridge. A failure during connection/preparation appears in job/health diagnostics before a data cycle begins. Start intended local listeners separately.
This phase covers real local OPC UA/Modbus TCP and existing virtual RTU regression. It does not newly qualify physical PLC/RS485, native Windows/Linux packages, network-fault appliances or endurance. Source scheduling, device logic and immediate readback can legitimately change data. Existing isolated-simulator/test-equipment terms apply. Installer archives are unchanged, and Phase 7 has not started.

## Stopping during protocol I/O
Stop preserves cancellation even when a protocol library reports a transport exception instead. A cancelled task cannot dispatch a follow-on request or enter reconnect recovery. Requests already dispatched without a response remain UNKNOWN; stopping does not prove that the remote device rejected them.
